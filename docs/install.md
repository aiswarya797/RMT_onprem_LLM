# Install and set up LLM Monitor

LLM Monitor is a read-only monitor for native Ollama on Apple Silicon Macs.
The supported runtime boundary is macOS 14 or newer, subject to qualification
on each exact Mac, macOS and Ollama combination. The current compatibility
manifest is unverified and there is no customer release yet.

## Same-machine preview

The default bundle supports **local** only. Remote roles, explicit inference,
request comparisons and external notifications are disabled by default.
Their implementation and existing data are preserved; see [experimental
workflows](experimental.md). The historical role instructions below apply only
to developers who explicitly opt in, not to preview users.

Download and extract the development bundle linked from the README. In the
extracted directory run `./llm-monitor-install.sh local`. The helper installs
for the current user and opens `http://127.0.0.1:9443`. Create the first local
administrator; pairing and the loopback Ollama target are automatic. No source
checkout or model API key is needed. This unsigned preview may need manual
macOS approval; never disable Gatekeeper to install it.

If Ollama is unreachable, open your existing Ollama app, then wait for the next
collection cycle. RMT does not start or modify Ollama. If port 9443 is occupied,
the helper reports the conflict without stopping the occupant. If the dashboard
is unavailable, run the status command below; use the packaged offline help
under `~/Library/Application Support/LLM Monitor/docs/` for recovery.

## Installation roles (remote roles are experimental)

Keep the generated installer helper beside the matching package and checksum
list. For a qualified release, keep the detached checksum signature, public
key and release verifier beside them too. Run one of these commands from that
folder:

```sh
./llm-monitor-install.sh local
./llm-monitor-install.sh master
./llm-monitor-install.sh collector --hub-url "https://MASTER-IP:PORT" --pairing-code "PAIRING-CODE"
```

The first command installs the dashboard, storage and collector on this Mac.
The second installs the dashboard and storage only, with a private TLS listener
for another collector. The third is the single command generated by the
master dashboard for a second Mac. It installs the collector, checks the
machine, completes certificate enrollment and starts its user service.

The helper verifies the matching package before installing it, runs the
role-specific compatibility check, starts the supported user service and
opens the dashboard for `local` and `master`. It prints the local status
command for `collector`. Users do not need Go, Node, a source checkout,
checksum calculations, manual configuration, certificate files or token-file
paths.

The helper is generated by the packaging build and is an unqualified local
development convenience when its package says development/unsigned. It must
not be described as a customer release. A publisher must provide the exact
signed, notarized artifact set and publish the public-key fingerprint and
Developer ID Installer identity through an independent channel before calling
the release qualified.

## First launch and pairing

For `local`, open `http://127.0.0.1:9443` if it does not open automatically.
The first-administrator page obtains the one-use setup handoff from the
loopback hub automatically. Choose the administrator username and password;
the handoff and password remain in memory and are not placed in the URL or
browser storage. If the handoff expires before setup, run:

```sh
"$HOME/Library/Application Support/LLM Monitor/bin/llm-monitor" admin bootstrap-renew
```

Return to the browser and choose **Check again**. The secret is never printed.

With the experimental developer opt-in, for `master`, the setup command prints the browser URL and the reviewed
private listener address. After signing in, **Connect another Mac** generates
one complete collector command and shows `Waiting`, `Connected`, `Expired`
or `Failed`. The reservation is one-use and expires after ten minutes. The
collector obtains the hub CA over its bounded bootstrap route, pins it in its
private application directory, then performs the existing mTLS enrollment.
No macOS trust store is changed and no remote command is executed.

For `collector`, paste the generated command into Terminal on the other Mac.
If the master cannot be reached, the code is expired, or the certificate
exchange fails, the command reports a plain-language retry action. The local
collector creates the safe loopback-only read-only target at
`127.0.0.1:11434`; target selection remains collector-side.

## What the dashboard means

The dashboard reports retained observations, with units, exact observation
times, current age and source quality. It distinguishes **This Mac** from a
**Remote machine** and shows:

- host identity and collector freshness;
- CPU busy ratio;
- memory pressure, compressed memory and swap used;
- available monitor-volume disk space;
- Ollama reachability, where reachable means only that the read-only endpoint
  responded;
- installed model identities beside runtime-loaded identities and digests;
- observed same-user process coverage and process history; and
- retained history, open incidents and unavailable capabilities.

Loaded means reported loaded by the runtime, not actively generating. A
reachable endpoint does not prove successful inference. Missing or stale data
is shown as unavailable or stale, never as zero. LLM Monitor sends no inference
requests in this phase, and there is no **Run Test** action. The future
request-run population will remain distinct from other application traffic.

## Check, retry and stop

Use the installed command for ordinary operation:

```sh
LLM_MONITOR="$HOME/Library/Application Support/LLM Monitor/bin/llm-monitor"
"$LLM_MONITOR" status
"$LLM_MONITOR" install check --role local
"$LLM_MONITOR" stop
```

Use `--role master` or `--role collector` when checking those roles. `stop`
only unloads LLM Monitor's own user services. It is safe to repeat and leaves
Ollama, its models and unrelated software untouched. Re-running setup preserves
the deployment, history and existing pairing; an explicit re-enrollment is
required before a retained identity can be replaced after restore.

## Uninstall

Preview the owned paths first. The normal choice keeps the protected database
and configuration for a later reinstall:

```sh
LLM_MONITOR="$HOME/Library/Application Support/LLM Monitor/bin/llm-monitor"
"$LLM_MONITOR" uninstall --keep-data --preview
"$LLM_MONITOR" uninstall --keep-data --deployment-generation "GENERATION-UUID"
```

Reinstall the same verified package and run its role helper again. Purge is
irreversible and requires the current deployment identity and generation:

```sh
"$LLM_MONITOR" status --json
"$LLM_MONITOR" uninstall --purge --preview
"$LLM_MONITOR" uninstall --purge --deployment-generation "GENERATION-UUID" --confirm-deployment "DEPLOYMENT-UUID" --backup-offer-acknowledged
```

Purge removes only the paths enumerated in its preview. It never removes
Ollama, models, Homebrew, another monitor or power settings. A collector on a
second Mac must be uninstalled on that Mac; the master does not execute a
remote uninstall.

A partial removal exits with code 6 and returns `retry_arguments`. Resolve the
reported local stop, permission or file-removal issue, then pass those exact
arguments to the same verified binary. The non-JSON output prints an
equivalent safely quoted `Retry:` command. Do not run `setup local` between attempts
and do not delete `removal-receipt.json` manually. If the final
receipt deletion failed after the binary was removed, restage the same
verified package or use its externally staged binary and run the returned
arguments.

## Verify a qualified release when publishing or auditing

Ordinary users use the generated helper above. A publisher or auditor can
verify the selected package offline with the existing verifier:

```sh
./packaging/macos/verify-release.sh \
  "./LLM-Monitor-0.1.0.pkg" \
  "./LLM-Monitor-0.1.0-SHA256SUMS" \
  "./LLM-Monitor-0.1.0-SHA256SUMS.sig" \
  "./LLM-Monitor-0.1.0-SHA256SUMS.pub.pem" \
  "PUBLISHED-PUBLIC-KEY-SHA256" \
  "Developer ID Installer: Example Corp (TEAMID)"
```

It binds the package to the signed checksum entry, checks the independently
published public-key fingerprint and installer identity, validates the
notarization ticket and Gatekeeper install policy, and confirms that only the
current-user installer domain is enabled. It must fail closed if any check
fails. The selected package command used by the verifier is:

```sh
LLM_MONITOR="$HOME/Library/Application Support/LLM Monitor/bin/llm-monitor"
installer -pkg "./LLM-Monitor-0.1.0.pkg" -target CurrentUserHomeDirectory
```

The checksum list also names the alternative archive and release manifest.
The archive cannot carry a stapled ticket; release mode binds it through the
detached signed checksum manifest and its contained signed binaries.

## Where data lives and updates

- Application, database and configuration: `~/Library/Application Support/LLM Monitor/`.
- Logs: `~/Library/Logs/LLM Monitor/`.
- User services: `~/Library/LaunchAgents/com.llm-monitor.*.plist`.
- Dashboard: loopback only. Collection continues while you are logged in; sleep
  and logout interrupt collection and must appear as gaps in history.

There is no automatic updater. Stop RMT, keep a backup using the operation guide,
then install a matching newer bundle. Preserve your data when reinstalling.
Do not downgrade a migrated database with an older binary; restore a matching
backup using the recovery guide. Ollama and its models are outside all of these
operations.

## Build and release prerequisites

The repository build is for maintainers, not ordinary users. It needs the
checked-in web lockfile, Node 22.22.2 or newer, npm 10.9 or newer, Xcode
command-line package tools and the verified Go 1.26.8 Darwin arm64 toolchain:

```sh
npm --prefix web ci --ignore-scripts --cache "$PWD/.work/npm-cache" --fund=false --audit=false
GO_BINARY="$PWD/.work/toolchains/go1.26.8/go/bin/go" \
SOURCE_DATE_EPOCH=0 BUILD_ID="development-local" \
  ./packaging/macos/build.sh development 0.1.0
```

Release mode additionally requires Developer ID Application and Installer
identities, an existing `notarytool` Keychain profile, a separate checksum
signing private key, the independently published checksum public-key
fingerprint and the independently published installer identity. In the
current environment those signing and notarization prerequisites are absent,
so the local build remains explicitly unqualified.
